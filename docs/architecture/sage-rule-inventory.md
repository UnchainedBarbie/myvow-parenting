## 2. Prompt-only enforcement gap

This section lists inventory items classified as **Core safeguard** or **Shared AI capability** whose enforcement depends wholly or partly on a prompt or on model behavior. Rules that the application already decides without asking the model are omitted here, including the draft gate, the single-objective clear, the legal-obligation rewrite, `usableOutboundBody`, the review receipt, proposal identity, recipient checks, and message immutability.

Sorted by risk, highest first. "ChatGPT or Claude called MyVow tools directly" means the model has tool access and does not receive Sage's system prompts.

| Risk | Rule | What happens without Sage's prompt | Application enforcement that would replace it | Effort |
| --- | --- | --- | --- | --- |
| 1 | Prompt injection boundary (Core) | The model treats co-parent text, parent paste, and tool results as instructions. It can be told to send, to widen a read, or to copy private notes into a draft. Nothing in the database stops that, because the text is ordinary content. | Keep message text in tool results, never in the privileged instruction channel. Reject any tool argument that is not in the server's allow-list for that turn (proposal id, conversation id, child id, file id). Do not execute a model-written SQL statement or a model-chosen case id. A schema check on the tool call is the replacement. A prompt sentence is not. | Large for a full instruction/data split. Medium for schema-validated tool arguments on the send and read tools. |
| 2 | Fidelity: parent turns are the authority (Core) | The model decides for itself that a draft "matches." It can send a broader, warmer, or different ask. The constant refusal sentence never runs, and the missed-reason log never runs. | Before a proposal is stored, run a server check that the body contains only facts from the parent turns and the authorized records for that turn, and that it still contains each material condition the parent stated. On failure, store no body and return the fixed sentence. Leave `fulfills` out of the tool result. | Large to replace the judgment completely. Medium to withhold any body the server cannot ground, which is the part that must exist before an external model can send. |
| 3 | Private strategy stays off the message (Core) | Private constraints, rejected approaches, and `private_objective` are visible if a tool returns them. The model can paste them into the draft. `draftExposesPrivateStrategy` runs only inside Sage. | Do not return `private_objective`, `grounded_in.private_constraints`, or `rejected` from any external tool. Before insert, diff the outbound body against those fields and refuse the send when a private-only phrase appears. Store the strategy on the proposal row, not in the tool payload. | Medium |
| 4 | Do not invent facts (Core) | The model fills in a time, place, amount, name, or agreement from its own knowledge. On the live chat path, invented logistics are caught only if the planner's `unsupportedFacts` runs. The conversation-action drafter relies on the prompt for everything that is not a legal-obligation phrase. | Run the existing fact check on every body before it becomes a proposal, including the conversation-action path. Reject a token that is a date, time, amount, or proper name unless it appears in the parent turn or in a row the server loaded for that turn. | Medium |
| 5 | Message kind routing (Shared) | The model picks its own tool. A calendar sentence can become a co-parent message, or a question can become a stored note. `parseActionInterpretation` never sees the call. | Each tool accepts only its own argument schema. The legal-obligation rule is a core safeguard and is already an application check (`unsupportedObligations`, `requestWithoutInstrument`). It is not in this table. An external sender still has to call those functions. The database will store the sentence if the tool skips them.

## 3. Data-layer safeguards

Inspected: `myvow-schema.sql`, `supabase/migrations/`, and `supabase/functions/`. This repo has no edge functions. Triggers and constraints run for every role, including the service role. Row Level Security does not. The service role bypasses RLS, and the current API routes call `getServiceRoleClient()`. An external tool that uses that client is not inside RLS. An external tool that uses the signed-in user's JWT is inside RLS.

### Already in the inventory, and already at the data layer

These protect an external integration automatically, including a service-role tool.

| Safeguard | Where | What it already stops |
| --- | --- | --- |
| No message delete | `myvow-schema.sql` `prevent_message_delete` | Any delete of `messages`, from any client. |
| No rewrite of message content | `restrict_message_update` | Changes to `original_content`, and changes to `ai_rewritten_content` after it is first set. Status fields can still change. |
| One send attempt | `supabase/migrations/20261028160000_messages_send_attempt.sql` unique index on `(sender_id, send_attempt_id)` | A retry of the same attempt inserting a second row. A new attempt id can still send the same words again. |
| Content hash | `hash_message_content`, `hash_expense_content` | A missing hash. This records integrity. It does not judge the words. |

The partial unique index on `messages.sage_proposal_id` (`20261105190000`) and the conversation-number freeze (`20261105170000`) are in the repo and protect every writer once applied. This inventory does not claim they are applied on the live database.

## 5. External AI read scope

The architecture proposal gives the model server-minted handles for events, expenses, documents, and children, plus the current message and working memory. It does not give the model a database connection. The lists below are the data types those tools could return if they follow the records the parent app already loads. File bytes, storage paths, and other cases were already excluded by that proposal.

### Child-entered data

| Data | Where it lives | Default for a first proof of concept |
| --- | --- | --- |
| Messages a child sent to a parent or sibling | Family message threads read by `app/api/kids/messages/route.ts` | Out of scope. |
| A child's Sage chat | `kid_sage_sessions` and the kids Sage routes | Out of scope. |
| A child's event request, including a photo | `event_requests`, kids event-request routes | Out of scope. |
| A child's calendar and custody view | `app/api/kids/calendar/events/route.ts`, `app/api/kids/custody-schedule/route.ts` | Out of scope. The parent calendar tool may return events the parent already sees. It does not call the kids routes. |
| Kid login material | PIN hash, invite tokens, `app/api/kids/pin/route.ts` | Out of scope. Never a tool result. |
| Child profile fields a parent saved | `children` first name, and the tone column `kid_sage_tone` | First name only, as a handle label. No tone, no PIN, no login state. |

### Co-parent-authored content

| Data | Where it lives | Default for a first proof of concept |
| --- | --- | --- |
| Inbound message body | `messages.original_content` where the direction is incoming | Out of scope for the first tool set. The parent can open the thread in the app. |
| Inbound email and attachments | Ingest and `inbound_uploads` | Out of scope. No file bytes. |
| Expenses, events, and documents the co-parent filed | Case tables, including rows with `visibility` of `private` | Out of scope unless the parent app would already show that row to this user. Private and parents-only rows of the other parent stay out. RLS will not do this for a service-role tool. |
| Co-parent display name and email | `case_members`, `users` | Out of scope. The recipient tool resolves the address on the server and does not return it to the model. |

### Private Sage conversations

| Data | Where it lives | Default for a first proof of concept |
| --- | --- | --- |
| This parent's Sage journal and session titles | `sage_journal_messages`, `sage_sessions` | Out of scope. Working memory may include the current draft the parent is looking at, not the journal history. |
| The other parent's Sage journal | Same tables, other `user_id` | Out of scope. A service-role tool must filter `user_id`. RLS does that only for a user JWT. |
| Proposal private fields | `private_objective`, `grounded_in` constraints and rejected lines | Out of scope. Not a tool result. |
| Coaching drawer and incident notes | `app/api/sage/chat/route.ts`, `app/api/sage/incidents/route.ts` | Out of scope. |
| Vows and cool-off | `vows`, `cool_off` | Out of scope for reading. Cool-off remains a server-side send check. |

### Recommended default for a first proof of concept

The model may read, for the signed-in parent and the current case only:

- Child first names, as labels on handles the server minted.
- Calendar titles and times the parent app would already show this parent.
- The current open draft body the parent is editing, and that draft's proposal id.

The model may not read child-entered messages or chats, co-parent message bodies, the other parent's private rows, either parent's Sage journal, court-order files, document bytes, storage paths, emails, or payment fields. Writes stay on today's proposal cards. The model does not insert into `messages`.

## 6. Decisions for the product owner

1. Will external tools run as the parent's JWT, or as the service role? RLS protects the first. It does not protect the second, which is how the API routes read today.
2. Is the first proof-of-concept read scope the short list in section 5 (names, visible calendar, current draft), with child-entered data, co-parent bodies, and private Sage left out?
3. May a parent send text that has no matching review, by acknowledging that? The gate allows it. An external model should not be able to set that flag.
4. After fidelity fails, may a body that still passes `usableOutboundBody` be shown as an unverified draft? That branch and the fixed refusal sentence disagree.
5. Which drafter is canonical, `conversation-action.ts` or `planner.ts`, and is the declarative register required for an external assistant or only for Sage?
